## 1. 起点与总体演进脉络

### 1.1 引擎起点

YalnEngine 是一个 Qt + Vulkan 的 C++ 渲染引擎，起点状态是经典的"教程式架构"：

```
YalnView（上帝类：串接一切）
  ├─ YalnVulkanInstance / YalnSurface / YalnDevice / YalnSwapChain
  ├─ YalnRenderPass / YalnGraphicsPipeline / YalnRenderer
  └─ YalnScene（扁平网格列表）
```

所有子系统是**具体类**，被 `YalnView` 直接持有；渲染管线硬编码（固定着色器路径、
固定描述符布局、固定飞行帧数、固定清除色）；场景是"一个网格数组"。

### 1.2 六次演进的动机链

每次重构都由上一个阶段暴露的不足驱动，形成一条清晰的动机链：

| 阶段 | 触发问题 | 核心动作 |
|---|---|---|
| 相机体系 | 相机行为耦合在透视相机里 | 接口/基类分层 + 派生家族 |
| 渲染配置化 | "想换管线参数就得改代码" | 不变流程与可变配置分离 |
| 子系统接口化 | "想换实现得改 View" | 纯虚接口 + 默认实现 + 双扩展机制 |
| 着色器抽象 | 着色器阶段写死、来源解耦 | 单着色器抽象 + 程序集合 + 规则校验 |
| 场景树 | 扁平网格列表表达不了层级 | 节点树 + 绘制项 + GPU 去重 |
| 节点家族 | 变换/行为语义混在 TRS 里 | 语义单一的节点类家族 |

**最重要的思考**：这不是六次独立重构，而是一个持续贯彻的架构策略——
**"不变流程"与"可变部分"的分离，逐层下沉**。

## 2. 第一阶段：相机体系重构

### 2.1 问题动机

原始代码只有透视相机，且位置/朝向/投影全部耦合在一个类里。需求出现：
正交投影（2D/CAD）、轨道环绕（模型查看器）、第一人称飞行（漫游）。

### 2.2 设计思考：继承策略"各取所需"

关键洞察是：不同派生相机需要复用的东西**不一样**——

- **换投影**的（正交）：需要复用 position/target/up + 视图矩阵逻辑；
- **换定位/朝向**的（轨道、第一人称）：需要复用投影矩阵逻辑。

因此不是单一基类，而是两级结构：

```
YalnCamera（纯抽象接口：proj/view/姿态）
 └─ YalnCameraBase（公共实现：position/target/up + lookAt 视图矩阵）
     ├─ YalnPerspectiveCamera      透视（投影在此实现）
     ├─ YalnOrthoCamera            正交 → 继承 Base，复用视图逻辑
     ├─ YalnOrbitCamera            轨道 → 继承 Perspective，复用投影逻辑
     └─ YalnFirstPersonCamera      第一人称 → 继承 Perspective，复用投影逻辑
```

**取舍**：正交相机提供 `setPerspective()` 做接口兼容映射
（`near·tan(fov/2)` 映射为可视半高），使正交/透视相机可互换而不惊动调用方——
这是"鸭子类型兼容"在静态类型下的落地方式。

### 2.3 轨道相机的关键设计：状态自洽

轨道相机内部状态只有 `yaw/pitch/distance`，位置由球坐标**推导**而非存储。
这带来一个重要的兼容性红利：`setPosition()` 反解出三个轨道参数，所以
QtViewer 已有的"旋转位置后调 setPosition"自动旋转逻辑**一行不改就能用**。

教训：**派生类的内部状态设计，要反过来考虑上层既有代码的交互路径。**

### 2.4 测试暴露的真缺陷

用 27 项单元测试验证时发现两类问题，处理方式体现了"先归因再动手"：

- 一部分 FAIL 是**测试脚本写错**（拿 proj×view 对比纯 proj 元素）→ 改测试；
- 一部分是**真缺陷**：`setTarget` 垂直看向时 `asin` 算出 ±90°，
  逃过了 ±89° 的限幅（限幅常量在各函数内局部定义，路径不统一）→
  统一为文件级 `kMaxPitch` 常量修复。

另一个测试发现的接口缺陷：`getProjectionMatrix()` 在接口中是 public，
但派生类覆写时收窄成了 protected——多态调用没事，具体类型直接调用被拒。
修复为保持 public 并注释契约。

**教训**：C++ 允许派生类收窄访问级别是个陷阱；覆写接口方法时应保持原访问级别。

## 3. 第二阶段：渲染流程配置化

### 3.1 问题动机

用户需求："后面可能需要定义不同的渲染管线、附件、描述符、渲染通道……
假设 YalnView 串接不变的流程，其他东西可以设置给 view，但要考虑异常情况与组合的合理性。"

这句话里藏着三个需求：**流程固定、参数可变、组合要校验**。

### 3.2 设计思考：什么该变，什么不该变

把初始化流程逐环节分类：

- **不变的**（流程骨架）：实例→表面→设备→交换链→渲染通道→管线→帧缓冲→渲染器
  的创建顺序、依赖关系、生命周期管理（成员声明顺序=创建顺序、析构逆序）；
- **可变的**（每个环节的参数）：深度附件开关、采样数、着色器、混合、飞行帧数、清除色。

结论：**流程留在 YalnView，参数做成纯数据配置结构体，在初始化前注入**。

```cpp
viewer.setRenderPassConfig(rpc);   // 深度开关/采样数/loadOp/finalLayout
viewer.setPipelineConfig(ppc);     // 着色器/拓扑/剔除/深度/混合/描述符绑定/推常量
viewer.setRendererConfig(rrc);     // 飞行帧数/UBO 绑定位/清除色
```

配置结构体的铁律：**纯数据、带 `makeDefault()`、默认值=旧行为**——
保证"不配置 = 什么都不变"。

### 3.3 设计思考：组合校验是"组合自由"的代价

参数一旦自由组合，就会出现非法组合（最经典的：管线开了深度测试但渲染通道
没建深度附件 → 运行时校验层报错甚至崩溃）。设计决策：

- 校验放在 **`YalnView::validateConfig`**，时机是设备+交换链创建后、子系统创建前
  （因为校验依赖设备能力与图像数量）；
- **一次性报告全部问题**，不是发现第一个就停——修配置时一次修完；
- 失败写入 `lastError()`，给人可读的原因，而不是让用户去读校验层日志。

| 检查项 | 拦截的错误组合 |
|---|---|
| 着色器文件可读/非空/4 字节对齐 | 路径错、半成品 SPIR-V |
| 推常量 4 字节倍数、≤ maxPushConstantsSize | 布局非法 |
| 描述符绑定位+类型不重复 | 布局冲突 |
| uniformBinding 必须存在于管线绑定 | 渲染器写不存在的绑定位 |
| 采样数：设备支持 + 管线与渲染通道一致 | MSAA 状态不一致 |
| 深度测试 ↔ 深度附件双向一致 | 经典崩溃组合 |
| maxFramesInFlight ∈ [1, 图像数] | 同步对象越界 |

### 3.4 设计思考：异常情况的分层处理

- `initVulkan` 整体 try/catch：`vk::SystemError` 转 `lastError()`，不冒泡；
- `drawFrame`/`recreateSwapChain` 各自兜底：帧循环异常跳帧不崩窗口；
- 渲染器内部防御性钳制：即使校验被绕过（直接调 renderer），飞行帧数也 clamp。

原则：**校验层拦截"能预防的"，防御性代码兜住"绕过校验的"，异常处理保住"意外的"。**

### 3.5 明确不做的事

顶点输入和子通道依赖图（多子通道）**刻意没有开放配置**：

- 前者牵动 Scene/Renderer 的缓冲布局，需要顶点布局描述进接口层；
- 后者建议等真正需要多通道渲染（阴影/后处理）时再引入渲染图概念。

**反过早抽象**：配置面每扩大一分，校验面就要扩大一片；没有真实需求驱动时，
配置项是负债不是资产。

## 4. 第三阶段：子系统接口化

### 4.1 问题动机

用户需求："把 8 个子系统都定义成接口，派生具体实现；在此之上更细致的设计
（比如着色器程序类）；注意对 Vulkan 的封装。不要完全丢掉之前的想法，
两者兼容——支持继承，同时提供一套默认实现，支持配置扩展。"

### 4.2 设计思考：三种扩展方式的统一

合并前两轮思路，得到一个统一模型：

```
抽象接口（零状态零实现）── 上层只依赖它
        ▲
默认实现（Vulkan 后端，原类名不变）── 可整体替换
        ▲
派生实现（继承：重写个别方法或全新实现）
        ＋
XxxConfig 配置结构体（配置：改参数不改类型）
```

**继承与配置不冲突而是正交的**：继承解决"换行为"，配置解决"调参数"，
同一个对象上两者可同时使用。

### 4.3 设计思考：接口契约里放什么

9 个接口（Instance/Surface/Device/SwapChain/RenderPass/ShaderProgram/
Pipeline/Scene/Renderer）+ 契约内容集中到 `yalninterfaces.h`：

- **共享值类型**：`YalnQueueFamilyIndices`、`YalnSwapChainSupportDetails`、
  `YalnFrameResult`、`YalnGpuMesh`——接口方法签名只暴露值类型与句柄访问器；
- **配置结构体**：三个 Config 移入接口头，作为契约的一部分
  （配置本身就是接口约定，实现类只留兼容别名如 `YalnRenderer::FrameResult`）；
- **不在契约内的方法不进接口**：如 `printCapacity()` 这类默认实现特有诊断，
  通过 `dynamic_cast` 探测——避免接口被实现细节污染。

**Vulkan 封装边界**：创建逻辑、依赖顺序、资源生命周期（深度附件的
image+memory+view 三件套）全部封在实现内部；跨头文件用前向声明避免循环依赖。

### 4.4 设计思考：View 的双机制并存

```cpp
// 方式一：继承替换（整体接管某个子系统）
viewer.setRenderer(std::make_unique<MyOfflineRenderer>());

// 方式二：配置定制（保持默认实现）
rpc.enableDepth = true; viewer.setRenderPassConfig(rpc);
```

关键防御：**initVulkan 之后替换实现会被拒绝**（返回 false + 告警）——
运行中偷换子系统会破坏资源生命周期，必须在入口拦住。

## 5. 第四阶段：着色器抽象

### 5.1 问题动机

用户问："IYalnShaderProgram 只能自定义顶点和片段着色器吗？我想支持所有
可自定义的着色器，但由我自己决定实现哪些，必须实现的要有强制要求。
是否可以抽象出 YalnShader 类？"

### 5.2 设计思考：单着色器与程序分离

原接口把"阶段集合"写死在程序里（vert/frag 双路径），正确拆法是两层：

```
IYalnShader          单个着色器：阶段 + 入口点 + 加载 + 模块生命周期
    ▲
YalnSpirvShader      默认实现：一个实例 = 一个阶段的 SPIR-V 文件
    ▲
IYalnShaderProgram   程序 = 着色器集合 + 组合规则 + type() 类型推断
    ▲
YalnSpirvShaderProgram  默认实现：addShader() 按需装配
```

这个拆分带来两个维度的自由：

- **阶段自由**：想加 Tess/Geometry 阶段就 `addShader()`，不加就没有；
- **来源自由**：内存嵌入、GLSL 运行时编译、热重载——都是新写一个
  `IYalnShader` 子类，程序层的规则校验自动复用。

### 5.3 设计思考："必须实现"如何表达

自由不等于无约束。规则放在**程序层**（而非视图层），因为规则依赖程序内容
与设备特性——程序知道自己有哪些阶段，也拿得到设备：

| 规则 | 性质 |
|---|---|
| 图形程序必须含 Vertex + Fragment | 引擎约定（Vulkan 规范允许无片元，需求出现再放宽） |
| TessControl ⇔ TessEvaluation 成对 | Vulkan 硬约束 |
| Tess/Geometry 需要设备特性 | 能力检查 |
| Compute 程序不得混入图形阶段 | 类型纯度（推断为 `Type::Mixed` 即非法） |
| 同阶段不得重复 | `addShader()` 添加时即拦截 |
| 空程序非法 | load() 时拦截 |

两个细节决策：

- 重复阶段在 **addShader 时就拒绝**（最早失败原则），load 时再兜底一次；
- 管线 `create()` 检查 `program.type() == Graphics`，Compute 程序被明确拒绝
  并提示"请使用计算管线"——类型推断为计算管线预留了扩展点。

### 5.4 关于"同阶段重复"的后续问答

用户追问"push 两个同类型着色器会怎样"——回答确认：默认实现在 `addShader`
处直接拒绝（返回 false + 打印原因），三道防线中最早的一道。同时指出一个
绕过点：拦截在默认实现里而非接口契约中，自定义程序实现若塞入重复阶段，
目前靠校验层兜底——建议将阶段唯一性检查提升到管线创建处（纵深防御）。

**教训**：约束写在实现里只保护默认实现；写进接口契约或下游消费方校验，
才能保护所有实现。

## 6. 第五阶段：场景树

### 6.1 问题动机

用户需求："设计一套完整场景树构建的类，实例程序改成 3 栋房子 + 完整地面。
Scene 包含根节点，节点分多种类型（普通/组/叶子），叶子只能包含可绘制对象。"

### 6.2 设计思考：从"网格数组"到"绘制项列表"

原渲染循环是 `for (i < gpuMeshes.size())` 用 `meshes[i]->getModelMatrix()`——
隐含了**网格与绘制一一对应**的假设。场景树打破这个假设（同一网格多处实例），
渲染循环的输入必须换成新概念：

```
YalnDrawItem { const YalnGpuMesh* gpuMesh; glm::mat4 world; }
```

这是从"每网格一次绘制"到"每实例一次绘制"的转变，也是将来实例化渲染
（一次 draw 画全部实例）的自然落点。

### 6.3 设计思考：节点类型的约束是运行期契约

```
YalnNode（普通节点：子节点 + 可绘制对象都可以有）
 ├─ YalnGroupNode   组节点：只能包含子节点（挂绘制项被拒绝）
 ├─ YalnLeafNode    叶子节点：只能包含可绘制对象（加子节点被拒绝）
```

约束机制：基类虚函数 `acceptsChildren()/acceptsDrawables()`，派生类覆写收紧。
违反时**拒绝并给出明确原因**（"叶子节点只能包含可绘制对象，拒绝子节点 xxx"），
而不是静默接受——错误的结构是建模错误，应当尽早暴露。

C++ 无法在编译期阻止"叶子上调 addChild"，运行期契约 + 明确报错是最务实的选择。

### 6.4 设计思考：三层变换组合

```
世界矩阵 = 父世界 × 节点 TRS × 绘制项局部 TRS
```

- 整栋房子移动/旋转/缩放 → 改组节点；
- 屋顶相对墙体的偏移 → 绘制项局部变换；
- `updateWorld()` 自顶向下递归，挂在 `drawFrame` 开头每帧执行——
  **运行时改任意节点变换，下一帧立即生效**（动画的入口）。

### 6.5 设计思考：GPU 缓冲按"唯一网格"去重

`buildGpuBuffers` 遍历树收集唯一网格指针，3 栋房子共享墙体/屋顶网格时
显存里只有 3 份缓冲；`update()` 收集绘制项时通过 `mesh→gpuMesh` 映射绑定。
配套防御：改树后忘记重建缓冲时，找不到 GPU 缓冲的绘制项被**跳过而非崩溃**。

### 6.6 兼容策略

`addMesh()` 保留为兼容扁平接口：等价于根节点下挂一个绘制项——
旧调用方（QtViewer）一行不改。

## 7. 第六阶段：节点家族扩展

### 7.1 问题动机

用户需求："添加更多节点类，比如位移、旋转等，根据不同场景需要实现更完整的节点类。"

### 7.2 设计思考：语义单一的"装配积木"

普通节点一套 TRS 混装三种变换，动画场景下互相干扰。拆成语义单一的节点族：

```
变换节点族：YalnTranslateNode（纯位移）
            YalnRotateNode（纯旋转：轴+角度，轴自动归一化）
            YalnScaleNode（纯缩放）
行为节点：  YalnSpinNode（绕轴持续自旋）
            YalnSwitchNode（N 选 1 开关）
            YalnBillboardNode（圆柱公告板）
```

每个类只取自己的分量（`localMatrix()` 覆写），链式组合：

```
rock（位移）→ rock.tilt（旋转 -18°）→ rock.size（非均匀缩放）→ 岩石网格
```

改倾斜不会扰动位置和大小——**各分量独立可调**正是动画/装配需要的。

### 7.3 三个行为节点的设计细节

- **YalnSpinNode**：内部 `steady_clock` 驱动，每帧累加 dt（clamp 0.1s 防跳变）；
  暂停时清空计时基准、恢复不追帧。取舍：节点自带时钟，换来主循环接口零改动
  （无需把 dt 从平台层一路传下来）。
- **YalnSwitchNode**：覆写 `updateWorld` + `collectInstances`，只遍历激活分支——
  未激活子树**既不更新矩阵也不产生绘制项**（不只是渲染时跳过）。
  这是经典场景图节点（OSG/Inventor），将来 LOD、日夜、装备变体都基于它。
- **YalnBillboardNode**：`updateWorld` 签名扩展携带相机位置
  （`IYalnScene::update(cameraPosition)`，渲染器从 `camera->getPosition()` 传入）；
  水平重合时保持上次朝向；几何约定为法线朝 +X 的薄片。

### 7.4 基础设施配套升级

- `localMatrix()` 虚化（变换/行为节点覆写自己的语义）；
- `updateWorld(parentWorld, cameraPosition)` 签名扩展（`virtual` 保证
  新行为节点无需改动场景层）。

### 7.5 示例场景验证

最终场景 19 节点：地面 + 3 栋房子（house2 用 Switch 提供尖顶/平顶两种屋顶）
+ 风车（TranslateNode 定位 + SpinNode 叶轮 120°/s）+ 公告板标记 + 变换链岩石。
带动画连续运行，校验层 0 错误。

## 8. 贯穿始终的设计原则

### 8.1 不变流程与可变部分的分离（总纲）

每一层重构都在回答同一个问题："什么是骨架，什么是血肉？"

- 流程骨架留在串接者（YalnView / YalnNode::updateWorld）；
- 血肉做成可注入的（Config / 接口实现 / Drawable / 节点类）。

### 8.2 默认值 = 旧行为

所有新引入的可配置点（三个 Config、着色器程序注入、场景树根节点）都保证
"不配置 = 什么都不变"。**兼容性是重构的生命线**——六个阶段每一步结束时
渲染行为都与之前一致。

### 8.3 约束与自由成对出现

| 自由 | 配套约束 |
|---|---|
| 配置参数自由组合 | validateConfig 组合校验 |
| 实现可替换 | initVulkan 后拒绝替换 |
| 着色器阶段自由装配 | 必须阶段 + 成对 + 设备特性规则 |
| 节点任意挂载 | 叶子/组/开关的 accepts 约束 + 同名拒绝 |
| 树随时修改 | 缓冲缺失的绘制项跳过不崩溃 |

### 8.4 最早失败 + 一次性报全

- `addShader` 阶段重复：添加时就拒；
- 组合校验：启动时报全部问题并写入 `lastError()`；
- 接口访问级别收窄：编译期就暴露。

### 8.5 反过早抽象

- 顶点输入配置化 → 等顶点布局描述进接口层；
- 多子通道/渲染图 → 等阴影/后处理需求；
- 节点类型不是越多越好 → 每个类型由真实场景驱动（风车驱动 Spin、
  多屋顶方案驱动 Switch、标记牌驱动 Billboard）。

## 9. 验证方法论

每个阶段都用同一套三层验证：

1. **单元测试**（相机阶段）：27 项——投影矩阵元素值、球坐标正反解、限幅、
   view×eye≈0、移动增量。测试本身也会写错，FAIL 要先归因再动手。
2. **编译链接**：增量构建，错误即修（raii API 差异、签名同步等）。
3. **运行验证**：起进程跑若干秒 → 检查退出码 → 收集 stdout/stderr →
   **校验层错误过滤（Validation Error / VUID-）必须为 0**。
   校验层是 Vulkan 开发最有价值的防线，每次改动后零错误是硬标准。

**默认路径回归**是每个阶段的固定动作：改完架构后用原始用法跑一遍，
确认输出逐字节一致。

## 10. 已知取舍与未来方向

### 10.1 已明确的取舍

| 取舍 | 理由 |
|---|---|
| 顶点输入固定为 `YalnVertexPC` | 改动牵动 Scene/Renderer 缓冲布局，待顶点布局描述进接口层 |
| 渲染图未引入 | 等多通道渲染（阴影/后处理）真实需求 |
| Spin 节点自带时钟 | 避免把 dt 从平台层一路传递；代价是暂停语义靠节点自觉 |
| 叶子约束是运行期的 | C++ 编译期无法表达"叶子不能有子节点" |
| 同阶段重复拦截在默认实现 | 提升到管线层是待办（纵深防御） |
| `getModelMatrix()`（网格自带 TRS）退化为遗留 | 变换职责已移交场景树节点 |

### 10.2 自然生长的方向

- **计算管线**：`IYalnShaderProgram::Type::Compute` 已预留类型判定；
- **实例化渲染**：绘制项已含 (gpuMesh, world) 对，同网格实例合并即可；
- **LOD 节点**：Switch + 相机距离判断即是；
- **序列/路径动画节点**：Spin 的时钟机制直接复用；
- **着色器热重载**：新增 `IYalnShader` 派生实现（文件监听 + 模块重建）；
- **跨子系统访问规范**：频繁 `static_cast` 到默认实现 = 该方法该提升进接口。
