# YalnEngine 灯光系统设计说明

> 版本：1.0（2026-11）　适用：yaln_core 当前主干
> 配套文档：《灯光使用说明》（docs/灯光使用说明.md）

---

## 1. 设计目标与约束

| 目标 | 落点 |
|---|---|
| 支持四类基础光源：环境光 / 平行光 / 点光 / 聚光 | `YalnLight` 继承体系 |
| 场景可加多盏灯，渲染时统一计算 | UBO 打包 + 片段循环 |
| **不改网格顶点格式、不改 GPU 缓冲、不改管线顶点输入** | 屏幕空间导数法线（见 §4） |
| 与既有架构一致：不变流程与可变部分分离，逐层下沉 | 光源定义在场景层，打包下沉到渲染器，计算下沉到着色器 |
| 上限明确、越界行为可预期 | 动态光源上限 `YALN_MAX_LIGHTS = 8`，越界截断 + 警告 |

**刻意的非目标**（防止过度设计）：阴影贴图、光照探针、PBR 材质、光源挂接场景树节点。这些是 v2 方向，见 §7。

---

## 2. 总体架构

```
CPU 侧                                  GPU 侧
─────────────────────────────────      ─────────────────────────────
YalnLight 继承体系                      shader.vert
  ├─ YalnAmbientLight                    ├─ 变换顶点 → 世界坐标 varying
  ├─ YalnDirectionalLight               shader.frag
  ├─ YalnPointLight                      ├─ dFdx/dFdy 求面法线
  └─ YalnSpotLight                       └─ Blinn-Phong 循环
        │
        │ IYalnScene::addLight()         ▲
        ▼                                │ UBO（每帧一次）
YalnScene::m_lights ── lights() ──► YalnRenderer::drawFrame
                                    打包 YalnFrameUniform（std140）
                                    write() → 每交换链图像一份 uniform 缓冲
```

数据只朝一个方向流动：**CPU 灯光定义 → 每帧打包 → GPU 循环计算**。
渲染器对光源类型"只知道怎么打包、不知道怎么算"，着色器对打包细节"只查字段、不整理数据"——几何约定（方向归一化、锥角换余弦）全部在 CPU 侧 `gpuData()` 完成。

## 3. 光源类型与语义

### 3.1 YalnGPULight —— GPU 打包结构（48 字节，std140）

```cpp
struct YalnGPULight {
    alignas(16) glm::vec4 position;  // 语义随类型变化
    alignas(16) glm::vec4 color;     // rgb = 光色
    alignas(16) glm::vec4 params;    // x=range, y=内锥cos, z=外锥cos, w=类型号
};
```

`position` 是全结构里唯一的"复用字段"，语义按类型分派：

| 类型 | position.xyz | position.w | params 使用 |
|---|---|---|---|
| Directional (1) | 光线**传播方向**（已归一化） | 强度 | 无 |
| Point (2) | 光源世界坐标 | 强度 | x = range |
| Spot (3) | 光源世界坐标 | 强度 | x = range, y/z = 内外锥余弦 |
| Ambient (0) | 不入灯光数组（独立通道） | — | — |

**设计取舍**：一个 48B 结构覆盖四种灯，8 盏灯 = 384B，加上矩阵/相机/环境光整个 UBO 544B，一帧一次 `write()` 搞定。代价是 `position` 字段语义复用——靠 `params.w` 分派，着色器里 `int(L.params.w + 0.5)` 一处分支解决。相比每类型独立结构（4 倍 descriptor 复杂度），这里选择"小而复用"。

### 3.2 环境光为何独立通道

环境光是"全场常量"，不是空间中的灯。若塞进灯光数组：8 盏上限被占、着色器每次循环多一次无效迭代。因此打包时把 `AmbientLight` 提取为 UBO 的 `ambient` 常量通道，动态光源数组只放 Directional/Point/Spot。

**多盏环境光的语义**：后添加的生效（打包逐盏覆盖）。这不是疏忽——环境光本就该只有一盏，覆盖语义比报错对迭代更友好。

### 3.3 衰减与锥形模型

- **点光衰减**：`atten = (1 - d/range)²`，range 外直接 `continue` 切除。
  选平滑二次而非经典的 `1/(1+kd+kq·d²)`：后者在 range 边缘仍有光晕（出现"被切断"的视觉缝），前者在 range 处归零，配合有限半径更干净，也是 UE 的做法。
- **聚光锥**：内锥角内全亮 → 内外锥之间线性过渡再平方软化 → 外锥外熄灭。软边公式 `t²` 让边界不出现"硬圈"。
- **高光**：Blinn 半程向量，指数 32（中等光泽），**高光用固定中性色**（约半强度白）而非顶点色——避免暖色材质被高光染得过艳。

## 4. 法线方案：屏幕空间导数（本次最重要的决策）

光照需要法线，但引擎顶点格式是 `YalnVertexPC`（位置+颜色），网格层没有法线属性。两条路：

| 方案 | 改动面 | 结果 |
|---|---|---|
| A. 顶点加法线属性 | 改顶点结构/属性描述/全部网格构造/GPU 缓冲布局 | 平滑着色，但波及全部既有代码 |
| B. **片段着色器 `cross(dFdx, dFdy)` 求面法线** | 只改着色器 | **平面着色（flat shading）**，零网格改动 |

选 B。理由：

1. `dFdx/dFdy` 是屏幕空间导数，对同一三角形内的所有片段，叉积结果恒定——这就是精确的面法线，对平面网格数学上无损；
2. 本引擎场景（村庄/山/树）是低多边形风格，**平面着色正是它想要的观感**：每个面明暗分明；
3. 改动面只有两个着色器文件 + 一处管线布局，风险极小。

**代价与边界**：将来引入平滑网格（球体高光过渡、角色模型）时，B 方案不能提供逐顶点法线。届时再走 A 方案（顶点格式加 normal 属性），平面着色可保留为可选项。这是明确的、可逆的技术债，见 §7。

**实现细节**：法线朝向由叉积顺序决定。实测 `cross(dFdx(p), dFdy(p))` 直接归一化即可正确照亮面向相机的面（背面已被剔除）。若未来出现"所有面都照不亮"的现象，修复方式是交换叉积顺序。

## 5. 数据流与时序

**每帧一次**（`drawFrame` 开头，acquire 之后、录制之前）：

```cpp
ubo.proj_view_mat = camera->getMatrix();
ubo.camera_pos    = vec4(camera->getPosition(), 0);
ubo.ambient       = 兜底(0.25,0.25,0.28) 或场景 AmbientLight 覆盖;
for (light : scene.lights())      // 环境光提取，动态光源截断于 8
    ubo.lights[i++] = light->gpuData();
ubo.counts.x = lightCount;
m_uniformBuffers[imageIndex].write(&ubo, sizeof(ubo));
```

- **打包成本**：`gpuData()` 是几个向量赋值，无堆分配、无同步——每帧微秒级，可忽略。
- **灯光动态性的边界**：修改光源属性（如移动路灯位置）**下一帧立即生效**，无需重建任何 GPU 资源——这是选"场景级光源"而非"烘焙"的直接原因。
- **环境光兜底**：场景一个灯都没加时 `ambient = (0.25,0.25,0.28)`——保证旧场景（未接灯光）不至于全黑，平滑兼容。

### 5.1 生命周期与所有权

- 光源由场景**独占所有权**（`unique_ptr`），`addLight()` 移交；
- `YalnScene::clear()` 一并清空灯光；`setRoot()` 不影响灯光（灯光不属于场景树）。

## 6. 管线布局的连带修改（校验层抓到的）

片段着色器开始读取 UBO 后，`YalnPipelineConfig::makeDefault()` 里 binding 0 的描述符必须从
`ShaderStageFlagBits::eVertex` 改为 `eVertex | eFragment`——否则校验层报
`VUID-VkGraphicsPipelineCreateInfo-layout-07988`（着色器资源变量与布局声明阶段不匹配）。

这是一条通用规律：**UBO 的内容增长会波及描述符布局声明**——布局不描述结构，但描述"哪些阶段可见"。以后每次给 UBO 加片段着色器要读的数据，都要检查这一处。

## 7. 局限与 v2 方向

| 现状局限 | v2 方向 | 说明 |
|---|---|---|
| 无阴影 | 方向光/聚光阴影贴图 | 深度通道已具备（深度测试已开），缺 shadow map pass |
| 平面着色，无平滑法线 | 顶点格式加 normal 属性 | 见 §4 的技术债；届时可按材质选择 flat/smooth |
| 光源不随场景树运动 | `YalnLightNode`（挂节点的光源） | 每帧 update 后从节点世界矩阵取位置/方向，再走现有打包路径 |
| UBO 循环上限 8 | 特化常量 / SSBO | 8 盏对当前场景足够；增长需求出现时再升级 |
| 无 HDR / 色调映射 | HDR 渲染目标 + ACES | 当前颜色直出，强光会截断到白色 |
